# 员工端周计划与日计划工作台重构设计

## 1. 背景与目标

当前员工端周计划和日计划在列表浏览、内容编辑和状态反馈上缺少统一的信息层级。

周计划编辑页采用连续堆叠的长表单，月计划来源、工作内容、交付物、验收标准和完成日期缺少稳定的语义分组；任务增多后定位和核对成本较高。日计划编辑页将日期、来源、状态、正文、风险、反馈和操作集中在一个页面中，主要填写任务与次要信息之间的层级不够清晰。两个列表页均以传统数据表格承载大量字段，待处理计划和下一步操作不够突出。

本次重构仅面向员工端桌面 Web，不修改后端接口、数据模型、数据库、权限规则和状态流转。目标是：

1. 让用户进入列表后快速识别当前计划、待处理事项和下一步操作。
2. 让用户围绕任务逐条编制周计划，围绕当天工作编制日计划。
3. 在保存或提交前持续展示缺失字段、日期限制和其他阻断问题。
4. 明确区分未保存、保存中、保存失败、草稿、待审批、通过和驳回等状态。
5. 保持周计划、日计划为独立页面，同时形成一致的工作台体验。

## 2. 范围与约束

### 2.1 本次范围

- 重构员工端周计划列表、编辑页和只读查看体验。
- 重构员工端日计划列表、编辑页和只读查看体验。
- 抽取周、日计划可共享的状态摘要、审批反馈和提交前检查组件。
- 增加前端未保存判断、字段级问题定位和更清晰的加载、空状态及错误状态。
- 保留手动“保存草稿”和“提交审批”，不引入自动保存。

### 2.2 非目标

- 不合并周计划和日计划路由或菜单。
- 不修改后端接口、请求参数、响应模型或业务校验。
- 不修改审批链、状态流转、日期规则或权限控制。
- 不实现移动端或触屏端专用布局。
- 不引入拖拽排序、批量导入、多人协作或离线编辑。
- 不重做全站视觉语言。

## 3. 设计原则

- **任务是核心信息单元**：周计划以周任务卡组织，日计划以当天工作为核心编辑区。
- **先状态，后细节**：周期、当前状态、待处理事项和主要操作优先展示。
- **每个状态一个主要动作**：避免编辑、提交、撤回、删除等按钮同时竞争注意力。
- **检查持续可见**：问题在编辑过程中实时暴露，并能定位到具体字段。
- **反馈使用展示语义**：审批意见和只读字段使用信息块，不伪装成禁用输入框。
- **保持一致但不强行合并**：周、日页面共享布局和交互规则，但保留各自业务特征。
- **后端校验为准**：前端校验用于即时反馈，后端仍是最终业务规则来源。

## 4. 方案选择

采用“任务卡片工作台”方案。

未采用增强型长表单，因为它虽然改动较小，但无法根本解决多条周任务连续堆叠、信息难以定位的问题。未采用分步向导，因为日常编辑和修改已有计划时需要频繁前后切换，效率较低。

周计划和日计划继续使用独立路由。列表页统一状态摘要和主操作，编辑页统一采用“左侧内容区 + 右侧粘性检查栏”，只读页沿用相同信息顺序并替换输入控件为展示组件。

## 5. 整体信息架构

每类计划包含三层页面体验：

1. **列表页**：回答有哪些计划、哪些需要处理、下一步做什么。
2. **编辑工作台**：左侧完成内容编制，右侧持续检查并执行保存、提交。
3. **只读查看**：按编辑页相同的信息顺序展示状态、反馈和计划内容。

统一页面规则如下：

- 顶部驾驶舱展示计划周期、当前状态、任务数量和唯一主要操作。
- 驳回意见和审批意见位于主要内容之前，并明确给出下一步提示。
- 草稿、驳回计划的主要操作为继续编辑。
- 待审批计划的主要操作为查看或撤回。
- 已通过及其他只读状态不展示误导性的编辑入口。
- 保存草稿和提交审批集中在编辑页右侧检查栏，页面顶部不重复放置。
- 用户离开存在未保存修改的页面前必须确认。

## 6. 周计划列表设计

### 6.1 页面结构

周计划列表由以下区域组成：

1. 页面标题和新建入口。
2. 当前周及待处理状态摘要。
3. 日期、状态和“只看待处理”筛选。
4. 计划摘要列表。

### 6.2 状态摘要

状态摘要至少展示：

- 当前自然周范围。
- 当前周计划是否已创建及其状态。
- 草稿或驳回数量。
- 待审批数量。
- 最近一次提交时间；不存在提交记录时不展示空占位。

### 6.3 计划摘要

每个计划使用紧凑摘要卡或具备卡片层级的行式列表，展示：

- 周一至周日的周期范围。
- 计划标题或从任务内容生成的摘要。
- 任务数量。
- 当前状态。
- 审批反馈摘要；无反馈时不占用固定高度。
- 提交时间等次要信息。

每个状态只突出一个主要操作：

- 草稿、驳回：继续编辑。
- 待审批：查看审批；撤回作为次级操作。
- 已通过及其他只读状态：查看计划。

删除等低频操作进入“更多”菜单。删除操作仍遵循现有状态限制和确认逻辑。

### 6.4 筛选与空状态

- 默认优先呈现当前周和需要处理的草稿、驳回计划，但不得改变接口返回数据。
- 保留周开始日期和状态筛选。
- 增加“只看待处理”快捷筛选，对当前已加载数据或现有查询条件进行前端组合。
- 明确显示筛选结果数量。
- 无数据时说明原因，并根据业务条件提供“新建周计划”或调整筛选入口。

## 7. 日计划列表设计

### 7.1 页面结构

日计划列表由以下区域组成：

1. 页面标题和主要编制入口。
2. 本周日期导航。
3. 当前日期状态摘要。
4. 可折叠的日期范围和状态筛选。
5. 日计划摘要列表。

### 7.2 本周日期导航

- 默认突出今天。
- 展示今天所在周的日期，并允许切换至前一周、后一周。
- 每个日期显示是否未编制、草稿、待审批、已通过或驳回。
- 点击日期后定位到对应计划；无计划时进入该日期的编制入口。
- 日期可用性继续遵循现有业务规则，不在前端放宽可编制范围。

### 7.3 日计划摘要

列表核心字段缩减为：

- 日期。
- 工作内容摘要。
- 计划状态。
- 风险等级。
- 直属领导反馈摘要。

点评状态、部门补审意见等次级信息放入可展开详情，不再长期占用横向宽度。核心内容不得仅依赖 tooltip 查看。

主要操作随状态变化：

- 当天尚未编制：编制今天计划。
- 草稿、驳回：继续编辑。
- 待审批：查看；撤回为次级操作。
- 已通过及其他只读状态：查看。

### 7.4 空状态

空状态使用可执行文案，例如“今天尚未编制日计划”，并提供对应日期的编制入口。筛选后无结果时说明当前筛选条件未找到记录，并提供重置筛选操作。

## 8. 周计划编辑工作台

### 8.1 布局

编辑页采用两栏桌面布局：

- 左侧为自然周和周任务编辑区，占主要宽度。
- 右侧为粘性检查栏，在页面滚动时持续可见。
- 1280px 宽度下不得产生页面级横向滚动。
- 较窄桌面宽度下检查栏可转为内容区底部，但操作顺序和校验能力保持一致。

### 8.2 自然周区域

- 新建计划时选择周一，并同时显示完整的周一至周日范围。
- 编辑已有计划时，如业务规则不允许修改周期，则使用只读文本展示，不使用禁用日期控件。
- 日期不可用范围继续复用现有前端限制和后端校验。

### 8.3 月计划来源选择器

来源选择器必须展示：

- 月计划月份。
- 月计划任务名称。
- 任务类型。
- 绩效权重。
- 已拆分周数。

选择器支持搜索。已被当前周计划其他任务使用的月计划条目不得再次选择，并应显示明确原因，而不是仅从选项中无提示消失。

### 8.4 周任务编辑卡

每条周任务使用独立卡片，固定包含四个语义区域：

1. **本周做什么**：本周工作内容。
2. **交付什么**：计划交付物。
3. **怎样算完成**：验收标准。
4. **何时完成**：计划完成日期。

卡片标题实时使用工作内容摘要。未填写时显示“待填写的周任务”，并保留任务序号。

每张卡片提供：

- 折叠或展开。
- 复制任务。
- 删除任务。

复制任务时不得复制月计划来源，避免立刻产生来源重复；工作内容、交付物、验收标准和完成日期可以复制，用户需重新选择来源。删除空白且未保存的新任务可直接执行；删除包含已填写内容的任务需要确认。删除已保存任务是否触发独立接口继续遵循现有页面和接口能力，不新增后端行为。

新增任务入口固定放在任务列表末尾。

### 8.5 实时校验

至少覆盖：

- 未选择自然周。
- 未选择月计划来源。
- 月计划来源重复。
- 本周工作内容为空。
- 完成日期不在当前自然周内。
- 完成日期早于现有业务规则允许的最早日期。
- 没有任何周任务。

交付物和验收标准是否阻断提交必须与现有后端规则一致。若现有接口允许为空，前端只给出非阻断提醒，不擅自新增必填规则。

## 9. 日计划编辑工作台

### 9.1 日期导航

页面顶部提供前一天、今天、后一天导航，日期选择器作为补充入口。

切换日期前：

- 无修改时直接切换并加载目标日期。
- 存在未保存修改时弹出确认，用户可取消切换或放弃修改后切换。
- 保存请求进行中时禁止重复切换，避免请求结果写入错误日期。

### 9.2 计划来源区域

关联月计划项、关联周计划来源和当前状态组成独立的“计划来源”区域。只读状态使用文本、标签和来源摘要展示，不使用禁用表单控件。

来源选项和可编辑性继续使用现有接口返回及状态判断。若当前接口只提供月计划来源，本次重构不虚构新的周计划关联字段；界面仅展示现有数据能够支持的来源关系。

### 9.3 主要编辑区

工作内容是页面主要输入区域，应提供：

- 清晰的字段名称和填写提示。
- 足够的默认编辑高度。
- 字数限制与剩余空间提示。
- 字段级错误状态。

风险、备注等次要字段独立分组。直属领导意见、部门补审意见和其他审批反馈使用只读反馈块展示，并按照重要性放在编辑区之前或之后，不与可编辑字段混排。

### 9.4 实时校验

至少覆盖：

- 未选择计划日期。
- 工作内容为空。
- 来源字段不满足现有接口要求。
- 日期不满足现有业务规则。

风险和备注是否必填完全沿用现有后端规则。

## 10. 右侧检查栏

周计划和日计划编辑页共享检查栏的交互规则，但展示各自的统计项。

### 10.1 展示内容

- 当前任务数量；日计划为当天计划状态和主要字段完成情况。
- 已填写关键字段数量或完整度摘要。
- 未保存、已保存、保存失败等本地编辑状态。
- 阻断问题列表。
- 非阻断提醒列表。
- 保存草稿和提交审批操作。

本次不引入自动保存，因此检查栏不得显示“自动保存中”等误导性状态。保存状态仅表示用户最近一次手动保存的结果，以及此后是否又发生修改。

### 10.2 问题定位

每个问题必须关联具体任务和字段。点击后：

1. 展开对应任务卡。
2. 平滑滚动到字段。
3. 聚焦可编辑控件。
4. 短暂强调字段边框，并显示简短错误说明。

仅弹出全局消息不能作为字段问题的主要定位方式。

### 10.3 保存与提交

- “保存草稿”为次操作。
- “提交审批”为主操作。
- 保存期间禁用重复保存和提交。
- 存在阻断问题时禁用提交，并在按钮附近说明问题数量。
- 非阻断提醒允许用户确认后继续提交。
- 提交前显示简短核对结果，不重复展示完整表单。
- 保存或提交失败后保留全部输入。
- 提交成功后的跳转行为沿用现有业务路径；周计划返回列表，日计划保持现有提交后只读查看方式。

## 11. 审批反馈与只读查看

### 11.1 反馈条

驳回和审批意见使用统一反馈条：

- 驳回反馈使用高辨识度但克制的错误色。
- 展示结论、意见正文和明确下一步，例如“根据意见修改后重新提交”。
- 普通审批意见也在同一区域展示。
- 没有反馈时不渲染空白反馈容器。

### 11.2 只读页面

只读页面沿用编辑页的信息顺序：

1. 周期或日期及当前状态。
2. 审批反馈。
3. 计划来源。
4. 任务内容或当天工作内容。
5. 风险、备注和其他次要信息。

所有内容使用展示组件，不使用大面积禁用输入框。长文本允许展开全文，核心信息不依赖悬浮提示。

## 12. 组件与代码边界

建议新增或抽取以下员工端组件：

- `PlanListStatusSummary`：列表页状态摘要。
- `PlanFeedbackBanner`：审批及驳回反馈。
- `PlanValidationAside`：问题列表、未保存状态、保存和提交操作。
- `WeekPlanTaskEditorCard`：周任务编辑卡。
- `DayPlanSourcePanel`：日计划来源及状态展示。
- `DayPlanDateNavigator`：日计划日期导航。

页面组件负责：

- 路由参数和页面导航。
- API 请求和响应映射。
- 保存、提交、撤回和删除等业务动作编排。
- 表单快照和未保存状态。
- 后端错误到字段问题的映射。

子组件通过明确的 `props` 和 `emits` 接收数据、上报编辑和操作意图，不直接调用业务 API。周、日页面可共享视觉和交互组件，但不强行抽象不同的数据模型。

## 13. 数据流与本地状态

### 13.1 加载

1. 页面读取路由参数。
2. 并行加载详情和现有来源选项；若接口之间存在依赖，则保持当前顺序。
3. 将接口模型映射为页面表单模型。
4. 完成回填后创建已保存快照。
5. 初始化实时校验结果。

### 13.2 未保存判断

- 使用稳定序列化或规范化后的表单快照比较修改状态。
- 忽略纯展示字段和请求状态。
- 保存成功后使用服务端返回结果更新表单及快照。
- 保存失败时不更新快照，因此页面继续显示未保存状态。
- 路由离开和日计划日期切换共用相同的未保存确认逻辑。

### 13.3 并发保护

- 保存、提交请求使用独立加载状态。
- 请求期间阻止重复业务操作。
- 日计划加载继续使用请求序号或等价机制，旧响应不得覆盖新日期数据。
- 保存响应只应用于发起请求时对应的计划和表单版本。

## 14. 错误与边界状态

- **列表加载失败**：显示错误原因和重新加载入口，保留筛选条件。
- **详情加载失败**：提供返回列表和重试操作，不渲染误导性的空表单。
- **来源选项为空**：说明缺少可拆解或可关联的上级计划，并提供可行的下一步说明。
- **保存失败**：保留输入，在检查栏展示失败状态和重试入口。
- **提交失败**：字段问题进入检查栏；无法定位的业务错误显示在提交操作附近。
- **撤回或删除失败**：刷新当前计划状态，避免页面继续显示过期操作。
- **只读状态变化**：若保存或提交时后端表明状态已变化，重新加载详情并明确提示用户。
- **空周任务**：编辑页至少保留一个空白任务卡；提交时按“没有有效任务”阻断。

## 15. 视觉与可访问性

- 延续现有浅灰页面背景、白色内容卡片和 Element Plus 基础控件。
- 蓝色仅用于主要操作、链接和当前焦点。
- 绿色表示通过或完成，橙色表示等待处理，红色表示驳回或阻断，灰色表示草稿或中性状态。
- 任务卡以克制的左侧状态边线或标题状态点区分，不堆叠过多高饱和标签。
- 标题、字段标签、正文、辅助说明形成稳定的四级文字层级。
- 键盘用户可以访问所有操作；问题定位后焦点必须进入对应控件。
- 禁用按钮旁必须存在可理解的禁用原因。
- 动效仅用于卡片展开、字段定位和状态切换，并尊重 `prefers-reduced-motion`。

## 16. 验收与测试

### 16.1 构建与静态检查

- 不新增无必要依赖。
- 不产生新的 TypeScript 隐式 `any` 或未使用变量。

- 草稿、待审批、通过、驳回状态的主要操作正确。
- 审批反馈长文本不会破坏布局。
- 删除和撤回继续遵循现有业务限制。

### 16.3 周计划编辑

- 新建、草稿和驳回计划正确回填并可编辑。
- 月计划来源搜索、不可重复选择和原因提示正确。
- 新增、复制、删除、折叠任务行为正确。
- 复制任务不会复制月计划来源。

- 点击问题可以展开、定位并聚焦对应字段。
- 未保存离开提示、保存失败保留输入和保存成功快照更新正确。
- 保存草稿、保存并继续编辑、提交审批及成功跳转符合现有流程。

### 16.4 日计划列表

## 17. 实施顺序建议

1. 抽取共享状态摘要、反馈条和检查栏的基础接口。
2. 重构周计划编辑页并验证任务卡、校验和未保存逻辑。
3. 重构周计划列表及只读详情。
4. 重构日计划编辑页和日期切换保护。
5. 重构日计划列表及本周日期导航。
6. 完成跨状态、长文本、错误恢复和桌面分辨率回归。

该顺序优先解决交互最复杂的周计划编辑，再将已验证的状态反馈和检查模式应用到日计划，降低同时修改多个页面带来的回归风险。
